# 审稿意见回应助手 — Response to Reviewers

## 核心理念

回信是写给**编辑**看的，不是写给审稿人看的——编辑才是做决定的人，回信的任务是让编辑不用重新翻审稿意见就能确认"每一条都被认真对待了"。

> 范围提醒：本skill处理的是收到R&R（修改后再审）决定之后的回应；如果是论文已经被**拒稿**、想申诉编辑决定，那是另一种文体（appeal letter），逻辑和策略都不一样，不在本skill范围内。

## 阶段1 — 意见整理与分类

把所有审稿人和编辑的意见整理成一张清单（可以用表格），每条标注：
- 来源（Reviewer 1 / Reviewer 2 / Editor）
- 类型：实质性问题（方法、理论贡献、结果解读）vs. 编辑性/次要问题（措辞、格式、参考文献）
- 按论文的**部分**（Intro/方法/结果/讨论）归类，而不是死板地按审稿人编号——两个审稿人常常用不同的话讲同一个问题，归到一起处理，回信里可以合并说明，也不会漏掉

## 阶段2 — 逐条应对策略

对每一条，选一种策略：

| 策略 | 什么时候用 |
|---|---|
| 完全采纳 | 审稿人是对的，照做 |
| 部分采纳 + 说明 | 部分建议合理，但完全照做会带来别的问题，采纳能改的部分，解释剩下部分为什么保留原样 |
| 礼貌但坚定地不同意 | 审稿人的理解有误，或建议跟研究设计的根本逻辑冲突——用证据/文献反驳，不是用态度反驳 |
| 提请编辑裁决 | 两位审稿人给出互相矛盾的要求，无法同时满足——明确写出这个矛盾，说明你选择了哪一边、为什么，请编辑裁决 |

**一个容易被忽略的技巧**：即使是"礼貌但坚定地不同意"的情况，也尽量在正文里加一句澄清性的补充，而不是完全不改一个字——这样下一个读者（包括未来的审稿人）不会再产生同样的误解。真正"完全不能做任何调整"的情况很少。

**真做不到的要求**：不要假装做了，老实说明为什么做不到，改成正式承认这是研究的边界/局限——这条直接对接`discussion-conclusion-writer`阶段4的局限性写法。

## 阶段3 — 回信撰写

### 3.1 结构

标准做法是逐条列出：审稿人原话（引用或转述）紧跟着回应，按审稿人分组、组内按顺序，方便编辑对照原始审稿意见核查。

### 3.2 常见的几个"礼貌开场"动作

- 开头感谢审稿人和编辑投入的时间与意见
- 说明已经逐条仔细处理了每一条意见
- 承认审稿意见切实提升了论文（这不是客套话，是让编辑感觉到你真的从中受益，而不是被迫应付）

### 3.3 语气

全程礼貌、不防御——审稿人是在批评论文，不是在针对你。哪怕某一条意见让人不快，回信里也不体现情绪。不同意时摆事实/摆文献，不摆态度。

## 阶段4 — 审稿人间意见冲突

明确点出冲突（"Reviewer 1建议扩大理论框架，Reviewer 2建议聚焦单一理论以增强内部一致性"），说明最终选择了哪一边、为什么这样选择更符合论文的核心定位，而不是含糊其辞、假装两边都听了。

## 阶段5 — 交付

用所在环境提供的文档生成能力（如 `python-docx` 库或 `pandoc` 转换；若环境中已有专门的 docx 技能，优先使用它）生成`.docx`格式的正式回信，可以附在修改稿前面一起提交。

## 重要原则

1. **写给编辑，不是写给审稿人**：语言和详略程度以"编辑一次看懂"为准
2. **不同意也要留痕**：即使反驳一条意见，也倾向于做一个小的文本调整，避免同样的误解在未来重演
3. **真做不到就老实说**：不假装采纳，改称为承认局限，接`discussion-conclusion-writer`
4. **意见冲突要摆到台面上**：不要偷偷选一边，要明确写出冲突、说明理由，必要时明确请编辑裁决
